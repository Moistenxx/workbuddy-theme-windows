# 逆向 WorkBuddy 外观机制的完整笔记

2026-10-10 实测记录。解决"改了没反应"的问题，全部来自读 `app.asar` 源码，不是猜测。

## 外观加载机制

程序里只有三个相关接口（在 `app.asar` 的 `appearance/handlers.ts`）：

```js
registry.handle("appearance:listResources", ...)
registry.handle("appearance:getSelections", ...)
registry.handle("appearance:setSelection", async (kind, resourceKey) => ...)
registry.handle("appearance:getLocalResource", async (theme) => ...)
```

云端接口（从 `daemon.log` 挖到）：
- `GET /v2/user-asset/appearance/get` → 当前选中
- `POST /v2/operation-platform/appearance/resources` → 主题目录
- base = `https://copilot.tencent.com`

### 加载流程

```
resolveDir(dirName)                    dirName = `${resourceKey}-${updatedAt}`
  → tryReadCachedCss(skin.css)          命中即注入，不重新下载 ★
  → 未命中才 downloadZip + 解压 + rewriteCssUrls
```

**关键**：`tryReadCachedCss` **不校验内容与云端包的一致性**，所以覆盖本地 `skin.css` 即可生效。

### 生效方式

App 启动时读一次，内存态不热更新。**设置→外观 切走再切回**即可重新读取（实测无需重启）。

## 已排除的无效路径（别再试）

| 尝试 | 结果 |
|---|---|
| 用户级 CSS 覆盖 `custom.css` / `user.css` / `--custom-css` | asar 内无实现（`custom.css` 命中的是编辑器 TextMate 语法文件，`injectCss` 是终端主题） |
| 改 app bundle 内的 CSS | **破坏代码签名，App 启动失败** |
| 注入 `--remote-debugging-port`（4 种方式：`open --args` / `open -na --args` / 手动主进程 / 直接跑 `MacOS/Electron`） | 启动器全部拦掉，端口不监听 |
| 直接调IPC 接口让脚本代替用户选中主题 | 接口不对外暴露（5 个端口全返回 No mapping found），且写的是**服务器端状态** |
| 从 `settings.json` / `user-state.json` / userData / plist / `workbuddy.db` 找主题配置 | 全部没有记录 |
| 猜 class 名 | **连续 5 轮全错**（详见下方教训） |

## 官方 CSS 速查（从 asar 提取）

提取方法：
```python
import re
d = open('/Applications/WorkBuddy.app/Contents/Resources/app.asar','rb').read()
txt = d.decode('latin1')
rules = re.findall(r'\.([A-Za-z0-9_-]+)\s*\{([^}]{0,300})\}', txt)
for sel, body in rules:
    if 'background' in body.lower():
        print(sel, re.findall(r'background[^:]*:\s*([^;]{0,60})', body))
```

### 区域划分靠属性，不靠 class

```css
.teams-container [data-view-id="sidebar"] { background: var(--wb-home-bg-primary); }
.teams-container [data-view-id]:not([data-view-id="sidebar"]) { background: var(--wb-home-bg-secondary); }
.teams-container.is-mac { --wb-home-bg-primary:#f2f2f2; --wb-home-bg-secondary:#ffffff; }
```

`data-view-id` 只有 `sidebar` 和 `detail-panel` 两个值。**对话页不属于 data-view-id 划分**，所以只改它会漏掉对话页。

### 需要半透化的变量清单

| 变量 | 服务于 | 备注 |
|---|---|---|
| `--wb-home-bg-secondary` | 首页/新建任务主区 | |
| `--wb-home-bg-primary` | 左栏 | |
| `--wb-bg-primary` | 对话页 `.claw-workspace` | |
| **`--wb-color-bg-primary-default`** | **`.cr-agent__body` / `.cr-frame__content`** | **最易漏** |
| `--cr-bg-canvas` | 会话画布 | 幽灵变量，官方 CSS 里无消费点 |
| `--cr-bg-primary-default` / `--cr-bg-secondary` | 会话内部 | |
| `--cb-bg-secondary` / `--cb-content-background` / `--cb-panel-bg-primary` | 面板 | |

真实消费点样例：
```css
.cr-agent__body      { background: var(--wb-color-bg-primary-default, #f2f2f2); }
.cr-frame__content   { background: var(--wb-color-bg-primary-default, #f2f2f2); }
.claw-workspace      { background: var(--wb-bg-primary); }
.cr-message-list-viewport / .cr-message-list__content / .cr-message-list__bottom-mask  ← 官方真实滚动容器类名
```

### 变量特异性陷阱

官方写的是 `:root, .cr-theme { ... }`：
- `.cr-theme` 是 class（特异性 `0,1,0`）**优先级高于** `:root`（`0,0,0`）
- 覆盖时必须写成 `:root, .cr-theme`，只写 `:root` 会被压掉

官方皮肤里还有 `body .teams-container.is-mac { --wb-home-bg-secondary:#f5f9ff }`，位置更靠前 → **覆盖必须加 `body` 前缀 + 放文件末尾**。

## 十一轮失败换来的教训

| 轮次 | 做了什么 | 结果 |
|---|---|---|
| 1-2 | 覆盖 `appearance-resources` 里已有的 3 个目录 | 无效——那是历史遗留，当前选中的是内置默认主题，**根本不加载 skin.css** |
| 3 | 改 `--cr-bg-canvas` | 无效——`d.count(b'var(--cr-bg-canvas)') == 0`，**App 里没有消费它的规则** |
| 4 | 改成 `:root, .cr-theme` 联合选择器 | 仍无效——真正刷底色的是 `--wb-color-bg-primary-default` |
| 5 | 打 `.claw-workspace__main` 等 class | 仍无效——该 class 不在此视图结构中 |
| 6 | 逐个枚举容器 + 官方基底被替换 | 界面样式崩坏（基底丢了），且中间仍白——官方有 522 个背景变量，逐个覆盖不现实 |
| 7 | 根层铺图 + 通配清深层 + 关键容器直接半透 | 两页都透，但中间仍有一块白，且背景被内容切成两段 |
| 8 | 给 15 个容器**每个**刷 `rgba(255,255,255,.25)` | 仍是白纱——**半透明叠加是乘法：25% 叠 3 层 = 58%，叠 4 层 = 68%**。这是「中间还是白纱」的真正根因 |
| 8b | 改用 `::before` 覆盖层 | 也不行——图片已烤一次白，再盖一层还是两层 |
| 9 | 白纱烤进图片（alpha 0.4）+ CSS 全透明 | 界面通了，但老板仍看到发白——**alpha 0.4 本身就是 40% 白** |
| **10** | **`--alpha 0` 纯透明 + 容器全 transparent** | ✅ 零发白，但老板反馈「看着那么糊」 |
| **11（最终）** | **`--blur 0` 关模糊 + 取消自动压暗 + 无损 PNG** | ✅ **原片零处理，像素级与源图一致** |

**核心教训**：
1. **不要猜 class 名，也不要从旧皮肤文件抄**——去 `app.asar` 挖官方 CSS 原文。
2. **找元素要看它"怎么画背景的"**，不是找它叫什么。搜 `background: var(--xxx)` 里的变量名。
3. **确认变量是否真被消费**：`d.count(b'var(--xxx)')`，为 0 就是幽灵变量。
4. **一套 skin 覆盖不只一个视图**。首页和对话页是不同结构、不同变量。
5. **变量多就用通配**。官方 522 个背景类变量，逐个覆盖必漏。
6. **CSS 层叠顺序**：清深层的通配规则要放在"给中层半透"之前，否则通配的 `transparent` 会盖掉半透。
7. **官方基底只能追加不能替换**，替换会丢全部官方样式。
8. **★半透明色叠加是乘法不是加法**：`1-(1-a)ⁿ`。25% 叠 3 层 = 43%，叠 4 层 = 68%。要"一次白纱"就把白烤进图片，别刷在多个容器上。
9. **调色必须从 base 重生成**，不能在同一张图上反复 mix。
10. **★★最根本的一条：老板说「透明」就是字面意思的 0，不是「淡淡的」**。`--alpha 0.4` 不是"透明 40%"，而是"加了 40% 白" —— 语义完全相反。**默认必须是 0**。
11. **想让字清楚就加模糊，绝不加白**：模糊是邻域平均，不引入白色；白纱是直接加白，会让整幅画面发灰发白。
12. **★★「原片一样清楚」=零处理**：不要自动压暗、不要默认加模糊、不要 JPEG 反复压缩。默认 `alpha=0, blur=0`，用**无损 PNG**，输出与源图**像素级一致**（可用 `ImageChops.difference` 验证最大通道差=0）。

## 目录结构

```
~/.workbuddy/appearance-resources/
└── theme-<resourceKey>-<updatedAt>/
    ├── skin.css                      ← App 实际读取的文件
    ├── assets/
    │   ├── welcome-bg/               ← 首页背景图槽位
    │   └── custom/                   ← 自定义图槽位
    └── workbuddy-skin-<name>/         ← 内层（zip 原始结构，官方备份）
        └── skin.css
```

- `updatedAt` 是服务器给的 epoch ms，**不是目录创建时间**（别误读）
- 缓存上限 8 个目录，LRU 按 mtime 淘汰
- 内层 `workbuddy-skin-*/skin.css` 可作为官方基底备份

## 图片资源槽位

| 变量 | 文件 | 用途 |
|---|---|---|
| `--wb-welcome-bg-image` | `assets/welcome-bg/*.png` | 首页整页背景 |
| `--wb-custom-img-main-content-welcome` | `assets/custom/img-*.png` | 首页内容区背景 |

**注入时相对路径 `./assets/...` 解析不到主题目录**，必须改写成 `local-file://<主题绝对路径>/assets/...`（App 的 `rewriteCssUrls` 就是干这个的）。

## 其他事实

- 真实 Electron userData 是 `~/.workbuddy/app`（从进程参数 `--user-data-dir` 确认），**不是** `~/Library/Application Support/*`
- 版本差异：≤5.6.1 主样式是 `skin.css`；**5.6.2 起改为 `skin.v2.css`**（覆盖正则要用 `^skin(\.v\d+)?\.css$`）
- 官方 CSS 有 512KB 上限（实测本作 59KB，远低于上限，不是截断问题）
- Python PIL 环境：`~/.workbuddy/binaries/python/envs/default/bin/python`（系统 python3 可能没有 PIL）
